# Club onboarding security review

Reviewed on 2026-10-02 on `feature/club-onboarding`. Scope: platform organization creation, verified identity matching, invitation discovery/claim/accept/decline/dismiss, CSV preview and confirmation, organization settings, member/role management, legacy access actions, email queue/worker, database constraints and browser-role RLS. No new product features or production changes.

## Findings and fixes

- **University mailbox verification:** Supabase auto-confirm can populate `email_confirmed_at` without mailbox control. Invitation responses now require a provider-issued confirmation-send timestamp followed by confirmation, matching Auth/database user ID and email, and no server-side skipped-verification marker. Auth settings must explicitly report email confirmation enabled; missing configuration, malformed settings and service errors fail closed. This also blocks historical auto-confirm accounts lacking confirmation evidence. Browser metadata is never proof.
- **Historical identity reuse:** Discovery previously returned every verified identity attached to the account, including a historical mailbox after a verified Auth email change. Only identities derived from the current verified provider address are eligible now. Historical associations remain immutable for audit; future SSO requires a separate verifier.
- **Unverified legacy decline and link privacy:** The legacy decline action and invitation page did not independently require mailbox verification. Both now require the same verified-account proof and Auth configuration. Legacy acceptance also checks provider/database identity consistency.
- **Legacy access paths:** Legacy acceptance could merge permissions into inactive membership records, and legacy removal deleted the membership tombstone used to reject older invitations. Acceptance now rejects inactive memberships; removal retains a `LEFT` record. Legacy invitation revocation checks grant authority for both legacy and identity-bound invitations. Adding a legacy member rechecks authorization after taking the organization transaction lock.
- **Suspension/ownership race:** A platform suspension's application-level owner checks were insufficient against simultaneous ownership promotion. A new database trigger prevents disabling the last enabled active owner. Ownership promotion locks and verifies the target account; membership changes retain the existing organization lock and last-owner guard. Concurrent transactions may safely abort instead of leaving zero enabled owners. Leadership management rechecks and locks the acting account in its transaction.
- **Defensive consistency:** Identity acceptance checks terminal timestamps as well as state. Legacy writers explicitly set invitation states and revoke only pending grants. The existing database trigger already synchronized legacy timestamps, so the timestamp discrepancy was not an exploitable revocation bypass. Workspace search now explicitly filters active memberships; existing inactive-capability constraints remain intact.
- **Request and CSV hardening:** Legacy access/onboarding object schemas reject extra properties. CSV parsing rejects replacement characters and malformed surrogate sequences rather than accepting corrupted decoding. Existing 1 MB, 1,000-row and 2,000-character cell limits, explicit headers, duplicate detection, formula-prefix rejection and server revalidation remain authoritative. No roster CSV export exists; any future export must escape every cell independently, including historical/raw audit values.
- **Independent RLS:** Onboarding tables already had restrictive deny-all browser policies. User, StudentProfile and Club already revoked browser access and had default-deny RLS; the migration adds matching restrictive policies so future permissive policies cannot accidentally expose identity/profile/organization records. No existing RLS is weakened.
- **Real Prisma regression:** Native PostgreSQL tests found nested roster row creates redundantly specified `clubId`, which Prisma rejects for the composite import relationship. Nested writes now inherit the organization ID from the parent relationship. SQL adapters were corrected to model that behavior; composite database foreign keys remain unchanged.

## Boundaries verified

- Recipient discovery and all invitation responses use authenticated provider identity, not profile computing ID, CSV account matches, manually submitted identifiers, URL possession or browser role checks.
- Organization IDs and target member/invitation IDs are scoped together. Organization-specific capabilities and owner flags govern grants; a global User role does not authorize onboarding. Ordinary members cannot manage rosters or roles; admins cannot appoint/replace owners.
- CSV imports create MEMBER invitations only, are additive, revalidate persisted inputs, and audit each outcome. Confirmation binds to the original uploader. Partial row errors do not bypass authorization or transaction/audit rollback.
- A shared organization row lock serializes claim, role change, invitation state change, import and email eligibility. Database uniqueness protects membership identity, pending identity invitations and active email attempts. Acceptance and audit are atomic; terminal states cannot reopen.
- Roster preview exposes account-match hints only to authorized leadership. Member management returns brief profiles and scoped invitations; ordinary members cannot retrieve this directory. Student settings/invitation discovery are scoped to the authenticated user/verified identities. Support impersonation remains an explicitly audited platform-admin facility, not an identity claim submitted by a student.
- Email sending remains explicit after import. Cooldown, sender/organization quotas, durable claim state and last-moment eligibility checks apply to manual API invocation too. The internal worker requires its configured bearer secret. Uncertain SMTP results are not retried automatically.

## Validation and operational limits

Regression tests cover auto-confirm and historical identity spoofing, malformed/oversized CSV and duplicate flooding, direct mass assignment, privilege escalation and foreign organization IDs. Migrated PostgreSQL/RLS tests use browser roles, including artificially permissive policies and table grants, to verify the independent deny boundary.

`tests/onboarding-concurrency.test.cjs` is opt-in through `OUTCLASS_SECURITY_TEST_DATABASE_URL`. It refuses non-local hosts and any database name other than `outclass_security_test`. It runs the actual server actions through Prisma with multiple PostgreSQL connections: double acceptance, competing owner designations, duplicate imports, double batch/worker requests, concurrent owner suspensions, and transfer versus suspension. Auth and SMTP are test doubles; no real invitation emails are sent. Normal `npm test` skips this test unless the dedicated local URL is supplied.

All migrations were replayed on disposable local PostgreSQL and the repository's PGlite migration tests. Complete tests, lint, typecheck and isolated production build were run. Production Auth settings/RLS were not queried or modified; deploy the additive migration through the normal migration pipeline. Accounts without provider confirmation evidence require review/reverification before accepting university invitations. Auth configuration lookup adds a fail-closed service dependency to invitation responses. Institutional SSO is not yet implemented and is not treated as email proof.

SMTP cannot participate in a PostgreSQL transaction. Persisted `SENDING` prevents automatic duplicate retries after ambiguous outcomes; a crash can leave an attempt requiring operator review. The browser database roles remain denied; Prisma/service credentials intentionally bypass RLS and must remain server-only. This review does not claim formal proof or live production penetration testing.
