## High

**H1 — Next's transitive Sharp remains vulnerable despite the direct dependency patch.** `pnpm-lock.yaml` resolves `. > next > sharp` to 0.35.4. `package.json` directly requests Sharp 0.35.5, but Node resolution from Next's package resolves 0.35.4 with librsvg 2.62.91; direct application resolution uses 0.35.5/librsvg 2.63.2. The [maintainer advisory](https://github.com/advisories/GHSA-wq5f-xc86-pv6w) describes possible RCE under specific Linux/runtime conditions when decoding SVGs and identifies 0.35.5 as patched. This audit did not execute a malicious image or establish that the deployed optimizer accepts an exploitable SVG. Treat this as an urgent vulnerable runtime dependency, not proven RCE. Remediate both resolutions, rebuild the production artifact and verify actual dependency resolution/image workflows on Linux. Roll back only to a known patched artifact. Verification: package resolution and registry advisory confirmed; unfixed.

**H2 — Production public-profile Prisma queries use `postgres`, a BYPASSRLS login.** `utils/prisma.ts:12–16` selects `POSTGRES_PRISMA_URL` over DATABASE_URL. The live role catalog shows `postgres.rolbypassrls=true`. A bounded before/after pg_stat_statements observation around one unauthenticated nonexistent-profile GET showed two matching Club query shapes increment once under `postgres`; see [runtime-role-probe.json](evidence/runtime-role-probe.json). Other traffic can contribute, so capture a direct role/connection identity in a controlled release before changing credentials. `outclass_production_app` already exists, is non-superuser/NOBYPASSRLS and owns application tables; ownership also bypasses their unforced RLS. Consequently neither role supplies per-user isolation to Prisma. Server guards are essential, and broad postgres additionally increases compromise blast radius. Remediate with a staged, least-privilege runtime/migration credential separation and exhaustive auth/storage/worker tests, with production approval. Do not enable FORCE RLS on these server-only tables without an explicit compatible policy design. Verification: role metadata and request-associated statistics confirmed; no SQL-injection or authorization bypass demonstrated; no credentials changed.

## Medium

**M1 — Ordinary account responses disclose internal decision-letter templates.** `app/api/users/me/route.ts:18–29` and `utils/current-user.ts:11–14` include full Club scalars for applications and memberships. `Club.decisionLetterTemplates` is therefore serialized to students and ordinary members. In contrast, `actions/communications.ts:154` requires `recruitment.manage` for the dedicated template reader. A real local HTTP/Auth/Prisma/PostgreSQL reproduction with two universities, two students and overlapping ordinary memberships returned the templates for both membership clubs and the student's application club, while correctly excluding the other student's application. See [account-projection.json](evidence/account-projection.json). This is API3 property-level disclosure, not a cross-student application leak. Replace full Club includes with one shared allowlisted account projection and align client types; keep internal templates behind their authorized loader. Test student/member/recruiter/owner responses, initial RSC payloads and organization switching. Verification: reproduced; unfixed.

**M2 — Two additional High dependency advisories and two Moderate Next advisories remain.** [dependency-audit.json](evidence/dependency-audit.json) reports five findings total:

Registry reports no patched release. Track upstream and bound untrusted CI inputs; do not claim a version bump fixes it. |
| `source-map-js@1.2.1` via Tailwind's build tooling | [High event-loop DoS](https://github.com/advisories/GHSA-68fv-2mgg-jv7q) | Build input exposure; patched version 1.2.2. Validate build output after the targeted update. |

Verification: registry scan, published advisories and resolved lockfile paths; no exploit execution. These are not five distinct demonstrated application exploits.

**M3 — Signup reveals a distinct existing-account branch.** `actions/onboarding.ts:32` returns a different message when Auth returns zero identities for an existing account. This may permit account enumeration. Recovery deliberately uses a common confirmation response, which is good. Normalize signup outcomes/timing within the intended email-confirmation UX and test the existing/absent-account cases locally. Verification: branch inspected and normal signup exercised; enumeration success against production was not attempted.

**M4 — Abuse coverage is incomplete at the application edge.** Live Vercel configuration has two active deny rules for retired deployment hosts/POST writers, no custom rate-limit rules, OWASP off and bot protection off. This does not mean platform DDoS mitigation is off: it is active. Provider Auth rate limits still apply, but were not retrieved in full. Claims, invitation/import/upload and expensive workspace reads need explicit observed-volume budgets; same-origin checks are not bot controls. Existing positive controls include serialized school-request limits, admin elevation attempts, report limits, invitation delivery limits and bounded bulk inputs. Stage targeted log-only rules, observe shared-campus-NAT traffic and only request blocking approval after reviewing false positives. Do not set a blanket campus-IP login limit. Verification: firewall CLI and source review; no production abuse test performed.

**M5 — Leaked-password protection is reported disabled by the live Supabase advisor.** Enable only after checking project support, UX/error handling and recovery behavior in staging. No password material was inspected. Verification: advisor warning; no setting changed.

**M6 — Expired provider-session deadlines were not enforced by ordinary application authorization.** The original guard relied on `getUser` and disabled status. Real captured-cookie tests subsequently showed logout/recovery denials already worked in this provider fixture, while an expired `auth.sessions.not_after` with an unexpired JWT still read the account and updated its profile. Local `getSessionUser` now verifies the exact candidate token, binds its UUID session claim to the verified subject, and checks row existence/deadline. Before: account 200 and write accepted; after: 401 and unchanged profile. One SQL query is added per authenticated request; one provider verification is retained. [Full evidence](session-revocation/README.md). Verification: fixed and tested locally, not deployed; production grants/provider compatibility and request-admission limits remain. [Supabase session guidance](https://supabase.com/docs/guides/auth/sessions) describes the underlying refresh-time enforcement contract.

## Low / defense in depth

- **L1 — Database function hardening:** 41 invoker functions lack fixed search_path. The only SECURITY DEFINER function, `handle_new_user()`, has an empty search_path but retains browser EXECUTE grants. It returns trigger, so the advisor alone does not establish a usable RPC escalation. Restrict EXECUTE and pin paths after a full trigger replay on staging. Browser/app roles have no public-schema CREATE privilege, reducing search-path substitution exposure. See [security-advisors.json](evidence/security-advisors.json).
- **L2 — Storage limits differ by entry path:** resume/headshot buckets are private and restrictive read guards work, but have null MIME/size limits. Owner-scoped INSERT policies allow direct provider uploads outside the server's validated action. Server paths enforce 10 MB PDF/5 MB raster limits; direct upload abuse and storage consumption remain untested. Add compatible bucket limits after inventorying existing files; keep restrictive policies. Existing signed read URLs can remain usable for their short validity period after a role/reference change.
- **L3 — Inconsistent error-response caching:** the live unauthenticated `/api/users/me` and cron denial responses have public/max-age=0/must-revalidate defaults, while successful account and workspace reads explicitly use private/no-store. No private cache leak was reproduced. Make private/no-store consistent on all auth-dependent branches and add response-header assertions. See [safe-production-http.json](evidence/safe-production-http.json).
- **L4 — Browser hardening/secret metadata:** HSTS and nosniff are present; no CSP/frame-ancestors or X-Frame-Options was observed. Introduce CSP in report-only mode before enforcement because inline boot/structured-data scripts exist. Vercel metadata lists RESEND_API_KEY as Config across production/preview/development; migrate its classification/scoping after reviewing consumers. No usable secret value was exported or demonstrated leaked.

## Controls verified and limits

All 78 application tables have RLS enabled. Effective anon/authenticated CRUD privileges are false on every public table, including migration bookkeeping. Forty-three no-policy advisor notices represent intentional browser denial here, not publicly readable tables. Restrictive storage policies constrain older permissive policies; all five buckets are private. No public/storage view bypass was observed. Full policy commands, grants and function definitions are in [the schema inventory](schema-inventory.md).

The main guards verify provider identity, confirmed UVA email, disabled accounts and live per-club capability grants. Platform access uses an independent allowlist, active DB grant, MFA and opaque HttpOnly/Secure/SameSite=Strict elevation bound to a verified provider session. The real onboarding suite passed recovery, TOTP and direct HTTP permission-denial cases. Native publication tests verify rollback, revocation and idempotency. Raw SQL inspected uses tagged parameters/Prisma.sql rather than unsafe interpolation. No `$queryRawUnsafe`/`$executeRawUnsafe` use was found in application data paths. Existing XSS defenses include React escaping and escaped structured JSON; no stored-XSS exploit was demonstrated. Sensitive mutations use Zod and ownership predicates, with remaining per-export review coverage limited by the inventory rather than a blanket proof.

The bounded [secret scan](evidence/secret-scan.json) inspected 551 reachable commits/5,395 blobs and 408 existing client artifact files. Its sole credential-URL match is a localhost placeholder in `docs/event-list-view.md:28`; no known local secret or high-signal provider credential matched. Only `.env.example` is tracked. This does not certify remote-only/unreachable history, unknown credential formats or deployed logs. Credentials were not rotated, decrypted or included in reports.

No aggressive scans, production test accounts, production writes or malicious uploads were used. Positive live role behavior was checked through catalogs and safe requests; non-production fixtures provide mutation tests. University-wide isolation and simultaneous native exclusive-slot booking need additional coverage described in [outstanding risks](05-outstanding-risks.md).
