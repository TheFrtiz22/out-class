# Account deletion (Phase 1)

Settings → Account → Delete account. Needed for the Privacy Policy deletion right and App Store 5.1.1(v).

## Flow
1. The person types their university email or `DELETE`, confirms in the shared danger dialog and proves fresh authentication. Accounts with a password (an `email` identity) must always re-enter it: it is checked on a throwaway Auth client and forwarded to Turnstile, with limits of 5 tries per account and 20 per network (a hashed IP in the audit row) per 15 minutes. Turnstile is off until configured, and the attempt limits hold either way; the shared limiter from PR #279 should replace the audit count once it lands. University sign-in only accounts have no password, so they need a sign-in within the last 10 minutes (the `amr` claim).
2. `requestAccountDeletion` writes a `PlatformReport` (`kind = ACCOUNT_DELETION`, the existing admin Reports queue) and an `AuditLog` row `account.deletion.requested` with `scheduledFor` (+14 days), then emails a confirmation over the invitation SMTP path. Cancel is a signed-in button (no bearer link; the unsubscribe-token pattern from PR #277 isn't on `main`).
3. Refused: Demo Mode, administrator support sessions (view-as), active platform admins, sole active owners of a club, and owners whose only other active owners have pending deletion requests too. Non-blocking warnings appear when the person is a club's only holder of `decisions.start`, the PRESIDENT role or the RECRUITMENT_LEAD role. If the confirmation email fails, Settings says so and the admin queue shows it.
4a. **Cancel needs no re-authentication**, by design. Cancelling only restores the account to how it was, so someone holding a stolen session gains nothing from it. Requiring a password would also make it harder for the real owner to stop a deletion that an attacker started.
4. `cancelAccountDeletion` works until the due date (report → `DISMISSED`, audit `account.deletion.cancelled`).
5. Admin → Reports lists pending requests with due dates and email status. **Complete deletion** requires fresh Admin verification (`requirePlatformAdmin({ fresh: true })`), a reason and an elapsed window. It runs `performAccountDeletion` (`utils/account-deletion.ts`), which a cron can call later. A club owner-guard trigger failure is shown as a plain message.

## What the procedure does (no migration)
The User row stays as the tombstone: email becomes `deleted-<id>@deleted.outclass.invalid`, `disabledAt` is set, and the Supabase Auth user is deleted. Every User relation is mapped in `userRelationDeletionPlan` (`lib/account-deletion.ts`); `tests/account-deletion.test.cjs` fails if the schema gains an unmapped one.

- **Deleted:** StudentProfile (+ experiences), résumé/headshot/attachment objects under `<userId>/` in `resumes` and `headshots`, task submissions and their `task-submissions` objects, RSVPs, saved events/clubs, tutorials, availability, drafts, calendar feed token, Web Push subscriptions (deliveries cascade, so devices stop receiving notifications), notifications, email deliveries, preferences, private club conversations, recipient-group entries, pending club claims, admin challenges, inactive admin grant.
- **Withdrawn:** in-progress applications with no club records depending on them.
- **Anonymized:** other applications keep the row, status and the club's own evaluations, interview records and observations (written by leaders, reaching the person only through the tombstone `studentId`). They lose their answers and anonymous-review text. Memberships with evaluations, interview records, panel assignments, annotations, ballots or overrides become `LEFT` with roles, permissions, titles and groups cleared; the rest are deleted. Decided claims lose their explanation. Club tasks and roster-row matches are unlinked.
- **Retained, pointing at the tombstone:** attendance, ballots (through the member row), decisions/letters, audit logs, reports, announcements and messages sent for a club, invitations sent, roster imports, panel and scheduling history.

Order: disable sign-in, then the DB transaction, then Storage removal, then the Auth deletion. Storage runs only after the transaction commits, so a rollback never leaves files missing. No trigger guards `ApplicationAnswer`, so answer deletion itself can't be refused. Task-file paths are kept in an `account.deletion.storage-pending` audit row so a re-run can still remove them. The Auth deletion is tried 3 times. On failure the audit row is `account.deletion.incomplete` with `authDeleted: false` and the request stays open. `requireAuth` never rewrites a disabled account's email, so a surviving session can't restore it. Every step is idempotent.

## What needs a migration (not done)
- **DecisionLetter.content and InterviewResumeDocument.content**: both are immutable by trigger (`DecisionLetter_immutable`, `interview_document_immutable`). The letter's salutation/body and the résumé snapshot bytes (stored in Postgres, not Storage) stay with the club. The procedure counts them (`retainedDecisionLetters`, `retainedResumeSnapshots`) in the audit row and the admin notice, and the Settings and email copy says so. Scrubbing them needs a migration that allows a tombstone-only redaction (for example, letter content replaced with a neutral `[deleted]` note and snapshot bytes cleared, when the application's student is disabled).
- **SchoolIdentity.userId**: `outclass_school_identity_guard` forbids unlinking verified ownership. A migration must allow `userId → NULL` when the User is a tombstone (or add a `deletedAt` on User the guard can check).
- **Personal data in immutable or retained rows**: `RosterImportRow.input` (immutable by trigger), `ClubInvitation.email`/`invitedName` addressed to the person, `SchoolIdentity.identifier`, `PlatformReport.summary` text they wrote, `ClubMessage.body` they sent for a club. Scrubbing these needs trigger changes or new nullable columns.
- **A true tombstone**: Restrict FKs from authored club records (ApplicantObservation, ClubAnnouncement, ClubMessage, panel/schedule history, InvitationDelivery, RosterImport and others) block deleting the User row. A shared tombstone user, or nullable FKs, would let the row itself go.
- **Request model**: the request reuses `PlatformReport`. A dedicated `AccountDeletionRequest` table would let a cron query due requests directly.

## Not verified here
Real Storage, Auth admin and SMTP calls, and DB triggers on a disposable database. The unit tests mock them.
